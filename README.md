# Твиттер

Продолжение лаб 3–5. Три REST-сервиса: пользователи, подписки и сообщения. У каждого своя PostgreSQL. Между сервисами только HTTP, доступа к чужой БД нет. Интерфейс сайта в задание не входит.

## Запуск

Нужен запущенный Docker Desktop в режиме Linux containers. В PowerShell из папки проекта:

```powershell
docker compose up -d --build
docker compose ps
docker compose logs --tail=30 users subscriptions messages
```

Первая сборка скачивает Java, Maven и зависимости. После старта контейнеров приложениям нужно несколько секунд на создание таблиц. Общий адрес API: `http://localhost:8080/api/v1`.

| Сервис | Прямой адрес | База с хоста |
|---|---|---|
| Users | http://localhost:9000 | localhost:5440/users_db |
| Messages | http://localhost:9001 | localhost:5441/messages_db |
| Subscriptions | http://localhost:9002 | localhost:5442/subscribers_db |

Пользователь и пароль баз для локальной лабы: `twitter` / `twitter`. Администратор: `admin@example.com` / `admin12345`. Настройки подключения, JWT и учётные данные администратора переопределяются переменными из Compose. Изменение пароля администратора в настройках не меняет уже созданного пользователя.

Остановить стенд с сохранением данных:

```powershell
docker compose down
```

Используются отдельные тома проекта `yashin-twitter`. База старого User Service не переносится и не изменяется.

## Запуск из IDEA

Открыть корневой `pom.xml` как Maven-проект, выбрать JDK 21. Запустить только базы:

```powershell
docker compose up -d users-db subscriptions-db messages-db
```

Затем запустить `UserServiceApplication`, `SubscriptionApplication` и `MessageApplication`. При таком запуске обращаться к сервисам напрямую на портах 9000, 9002 и 9001. Если приложения уже запущены в Docker, сначала остановить их: `docker compose stop gateway users subscriptions messages`.

Сборка без запуска:

```powershell
.\mvnw.cmd package
```

Если Java не найдена, указать свою JDK 21 через `JAVA_HOME`. Maven устанавливать отдельно не нужно.

## Структура

```text
user-service/          пользователи, роли, JWT; JPA
subscription-service/  подписки, списки и статистика; JdbcTemplate
message-service/       сообщения, реакции и лента; JdbcTemplate
postman/               коллекция запросов
docker-compose.yml     три приложения, три БД и nginx
nginx.conf             маршрутизация общего API
.github/workflows/     сборка Maven и проверка Compose
```

Внутри сервисов: controller → service → repository. DTO — Java records. В новых сервисах SQL из лабы выполняется через JdbcTemplate. Общая библиотека, брокер и service discovery не нужны.

## Пользователи

Все пути ниже относительно `/api/v1`.

| Метод | Путь | Права |
|---|---|---|
| POST | /users | регистрация |
| POST | /auth/login | вход |
| GET | /users/{id} | публичный профиль |
| GET | /users?ids=1,2 | пакетная выборка |
| PATCH | /users/{id} | владелец или administrator |
| PUT | /users/{id}/roles/{role} | administrator; повтор безопасен |
| POST | /users/{id}/roles | прежний способ выдачи роли |
| DELETE | /users/{id}/roles/{role} | administrator |

Регистрация выдаёт `subscriber`. Для публикаций администратор назначает `producer`. После изменения роли нужно **войти заново**: роли записаны в JWT. Срок токена по умолчанию один час. Пароли хранятся как bcrypt-хеши, email нормализуется в нижний регистр.

## Подписки

| Метод | Путь | Назначение |
|---|---|---|
| POST | /subscribers/my/{authorId} | подписаться; нужен subscriber |
| DELETE | /subscribers/my/{authorId} | отписаться |
| GET | /subscribers/my/{authorId} | проверить подписку |
| GET | /subscribers/my | id авторов для ленты |
| GET | /subscribers/users/{userId}/authors | на кого подписан пользователь |
| GET | /subscribers/users/{userId}/subscribers | кто подписан на пользователя |
| GET | /subscribers/users/{userId}/stats | счётчики |

Операции `/my` требуют Bearer-токен. Остальные методы публичные. Списки принимают `page` и `size`. Пустой список для неизвестного пользователя допустим по лабе 4.

Подписка на себя запрещена (`422`), повторная подписка даёт `409`. При подписке Users проверяет существование автора и роль producer; отписка работает без Users.

## Сообщения и реакции

| Метод | Путь | Назначение |
|---|---|---|
| POST | /messages | публикация; нужен producer |
| GET | /messages/{id} | сообщение и счётчики реакций |
| PATCH | /messages/{id} | изменить текст; только автор |
| DELETE | /messages/{id} | удалить; автор или administrator |
| GET | /messages?authorId=2 | сообщения автора |
| GET | /messages/feed | лента подписок; нужен токен |
| PUT | /messages/{id}/reactions | поставить или заменить свою реакцию |
| DELETE | /messages/{id}/reactions | убрать свою реакцию |
| GET | /messages/{id}/reactions | счётчики и myReaction при переданном токене |

Создание и изменение: `{"text":"Моё сообщение"}`. После обрезки пробелов текст должен содержать 1–2000 символов. Автор берётся из JWT.

Реакция: `{"type":"like"}`. Допустимы `like`, `dislike`, `heart`, `laugh`, `sad`. На сообщение у пользователя одна реакция; повторный PUT заменяет её. При удалении сообщения реакции удаляет БД.

Сообщения автора и лента принимают `page=0&size=20`, size от 1 до 100. Ответ: `{"items":[],"page":0,"size":20,"total":0}`. Порядок: createdAt DESC, id DESC.

## Межсервисные вызовы

Messages получает у Subscriptions `authorIds`, передавая исходный Authorization, и читает сообщения только из своей БД. Subscriptions проверяет автора в Users, а для списков получает имена одним пакетным запросом. Все три приложения проверяют JWT локально с одинаковым ключом.

Ошибки имеют вид `{"message":"…","details":{},"timestamp":"…"}`. Неверный токен — 401, недостаточно прав — 403, отсутствующая запись — 404, конфликт — 409, нарушение бизнес-правила — 422. Недоступность необходимого соседнего сервиса — 503, а не пустая лента. Таймаут соединения 2 секунды, чтения 3 секунды. После перезапуска контейнера межсервисные запросы могут ещё до 30 секунд возвращать 503, пока обновляется DNS-кэш Java.

## Проверка в Postman

Импортировать `postman/twitter.postman_collection.json`. Запросы выполняются вручную в порядке папок. Коллекция сохраняет id и токены в переменные автоматически. Для повторной регистрации изменить переменную `run`, чтобы email был новым.

1. Войти администратором, зарегистрировать автора и читателя.
2. Выдать автору producer и войти обоими пользователями.
3. Опубликовать сообщение, проверить чтение и редактирование.
4. Подписаться читателем, проверить авторов, подписчиков, статистику и ленту.
5. Поставить like, заменить на heart: общее число реакций должно остаться 1.
6. Попробовать изменить сообщение читателем: 403. Подписаться повторно: 409. Подписаться на себя: 422.
7. Убрать реакцию, отписаться и убедиться, что лента пуста. Удалить сообщение автором.

Проверка недоступности Subscriptions:

```powershell
docker compose stop subscriptions
# Запросить ленту с токеном: ожидается 503.
docker compose start subscriptions
```

Проверка недоступности Users:

```powershell
docker compose stop users
# Запросить сообщения автора или создать подписку: ожидается 503.
# Чтение сообщения по id и уже выданные JWT продолжают работать.
docker compose start users
```

## Отличия и ограничения

Сохранена совместимость с предыдущим User Service: пакетная выборка публичная и возвращает массив; операции с ролями возвращают профиль. Поэтому публичные списки подписок могут получать имена без служебного аккаунта. В плане лабы 4 были защищённый batch с обёрткой items и ответы 204 для ролей. Фактические контракты выше согласованы между тремя сервисами.

Базы и приложения рассчитаны на локальную учебную работу. JWT не отзывается до истечения срока; после снятия роли старый токен действует до часа. Удаления пользователей нет, поэтому очистка их данных в других сервисах не реализована. Таблицы создаются идемпотентными schema.sql, полноценной системы миграций нет.
